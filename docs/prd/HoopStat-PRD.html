1. Ringkasan Eksekutif

HoopStat (brand di UI/landing: HoopStats) adalah platform analitik basket remaja yang mencatat play-by-play secara live atau dari video YouTube, membangun ulang possession dan lineup, menjalani pipeline produksi tracking → QA → coach → publish, lalu menampilkan box score, advanced stats, shot chart, match story, dan umpan balik AI Coach berbasis Gemini.

Produk ini menargetkan ekosistem basket usia dini hingga junior Indonesia (KU-8 sampai KU-19, Putra/Putri/Campuran) dengan bahasa operasional klub/akademi (termasuk nuansa DBL). Pengguna utama: orang tua/wali, pelatih, statistician profesional, scout, dan super-admin operasional.

Status produkPrototype offline-first yang sudah kaya fitur, belum production-ready (auth lokal, pembayaran simulasi, sync cloud dimatikan).
Inti diferensiasiPrompt-flow modular untuk tracking cepat + pipeline QA/coach + klaim atlet berbayar + jasa statistik YouTube.
Keputusan PRD iniMendokumentasikan as-is sebagai baseline, lalu menetapkan target produk yang harus dibawa ke produksi.
Satu kalimat produk. HoopStat adalah sistem operasi statistik basket remaja: dari ketukan di bangku cadangan sampai profil atlet terverifikasi yang siap dilihat scout.

Dokumen ini adalah PRD lengkap sekaligus paten desain resmi (Bagian II). Bukan ringkasan pemasaran. Setiap requirement merujuk kondisi kode saat audit (Agustus 2026): React SPA + Express OCR + IndexedDB hoopstats-db v24. Fitur baru wajib merujuk DP-xx dan BP-xx. Bagian “Status” memakai badge:

  • AS-IS sudah diimplementasi dan dapat dipakai lokal
  • PARSIAL ada UI/logic, belum lengkap atau belum terhubung
  • GAP dijanjikan di landing/komentar, belum ada implementasi nyata
  • TARGET requirement produksi yang harus dibangun

8. Alur Pengguna

8.1 Customer / orang tua

Landing→ Signup customer→ Buat anak / Klaim→ Bayar 50–250rb→ Admin approve→ Stats / Story / Services
  1. Masuk dari /welcome (bisa isi lead) atau /signup sebagai customer.
  2. Di /profiles membuat profil anak atau klaim: search → teaser PPG/RPG/APG → form hubungan (ayah/ibu/wali) + dokumen KK/akta/kartu pelajar → pilih paket → pembayaran (saat ini selalu sukses) → status pending.
  3. Admin menyetujui di /admin/claims: claimStatus: verified + AthleteLink.relationship = guardian. Toast “Klaim … disetujui/ditolak”.
  4. Home menampilkan tren dan highlight. Customer tidak dapat membuka tracker (desain: tidak punya track_match).
  5. Dapat memesan jasa di /services (Rp 50.000) atau melihat /stats dan story jika wali atau sudah bayar.
  6. Opsional apply jadi statistician/coach di /account/apply.
Konflik produk. Landing menjanjikan “Self-tracking pertandingan” di paket Gratis, tetapi role customer sengaja dilucuti track_match. PRD menetapkan keputusan di §12.4.

8.2 Statistician

Login→ Inbox tugas→ Buat match dari request→ /track/:id→ Submit QA
  1. Dashboard default adalah inbox (StatTasksPage).
  2. Membuka request assigned → createMatchFromRequest → /track/:gameId.
  3. Mencatat dengan video, prompt, clock sync, AI lineup; lalu advance ke qa_review.
  4. Jika dikembalikan QA, memperbaiki dan submit ulang.

8.3 QA

  1. Masuk /workspace?tab=qa atau /qa/:matchId.
  2. Jalankan auditMatchIntegrity (healthScore 0–100, TRUSTED / CAUTION / UNRELIABLE).
  3. Enrich shotZone, assistType, phaseOfPlay, pressureLevel.
  4. Checklist skor / anomali / lineup → advance ke coach_analysis atau return ke tracking dengan catatan.

8.4 Coach

  1. /workspace?tab=coach → /coach-analysis/:matchId.
  2. Anotasi pada possession/event/player/team/game (kategori skill/strategy/decision/teamwork/effort/mental, rating 1–5, timestamp video).
  3. Publish → /story/:matchId.
  4. AI Coach di /stats?tab=aicoach; Fundamentals untuk perpustakaan drill.

8.5 Scout

Hanya /gallery dan story/profil yang published + discoverable. Tidak dapat track, request, atau kelola profil. Apply scout tidak tersedia di UI (tipe data mengizinkan, halaman apply hanya statistician/coach).

8.6 Admin

Control center dengan badge klaim/aplikasi pending. Mengelola klaim, role-app, curations, CRM, CMS, RBAC, user, atlet, laga, prompt editor, dan assignment jasa.

20. Status dokumen sebagai paten desain

Mulai versi 2.0, dokumen ini adalah System Design Pattern Patent HoopStat. Artinya:

  1. Setiap fitur baru harus memakai salah satu pola DP-01 s/d DP-16, atau mengajukan amandemen pola baru lewat §32.
  2. Dilarang membuat alur tandingan untuk klaim, pembayaran, pipeline, visibilitas match, atau identitas atlet.
  3. Nama state, permission, dan SKU di UI wajib sama dengan katalog ini.
  4. Kalau kode as-is menyimpang dari paten (ditandai GAP), yang menang adalah kolom Paten (wajib) — kode harus ditarik ke paten, bukan sebaliknya, kecuali amandemen disetujui.
  5. Business process BP-xx adalah kontrak operasi: QA, admin, dan statistician bekerja menurut langkah ini.
Prinsip utama paten. Satu kebenaran identitas atlet. Satu pipeline produksi. Satu matriks visibilitas. Satu katalog SKU. Event play-by-play adalah sumber, statistik adalah turunan. Manusia (QA/coach) mengunci kepercayaan; AI hanya membaca data terstruktur.

21. Katalog Design Pattern resmi

Enam belas pola di bawah ini adalah IP operasional sistem. Implementasi boleh berganti teknologi (IDB → Postgres), tetapi bentuk pola tidak boleh pecah.

DP-01 — Prompt-Flow Event Capture

Masalah. Mencatat basket full-game dengan tombol datar menghasilkan event yatim (tembakan tanpa rebound, skor tanpa assist).

Pola. Setiap aksi pemicu membuka PromptFlow: container berantai dengan primary action, secondary action (aktor/pilihan), optional field (gated lite/detailed), dan branching. Event yang dihasilkan membawa sourceType, promptFlowId, promptStepId.

Aturan paten. Jangan menambah tombol event baru di tracker tanpa mendaftarkannya ke flow library. Admin mengubah urutan lewat Prompt Flow Editor, bukan hard-code di komponen.

Flow wajib: plus_2pt, plus_3pt, missed_shot, missed_free_throw, turnover, rebound, defensive_foul, offensive_foul, substitution, timeout, jumpball, standalone_steal, standalone_block, anomaly_missing_event + override single-player.

DP-02 — Dual Recording Axis

Dua sumbu independen, jangan digabung jadi satu enum:

  • Cakupan recordingType: single (satu anak) · team (satu tim) · full (kedua tim).
  • Kedalaman recordingMode: lite (wajib saja) · detailed (zona, contest, pressure, phase).

Harga jasa dan SLA boleh berbeda per kombinasi, tetapi data model tetap dua field ini.

DP-03 — Stint Integrity (tepat 5)

Lineup sah = tepat 5 playerIds dalam satu MatchStint dengan jendela clock. Substitusi menutup stint lama dan membuka stint baru. Stint durasi 0 = isGhostStint. Event yang pemainnya tidak ada di stint aktif = temuan audit PLAYER_NOT_ON_COURT. 3x3 memakai aturan yang sama dengan ukuran lineup 3 — jangan pecah entitas, parameterisasi jumlah.

DP-04 — Possession as Derived Truth

Possession bukan diinput manual sebagai sumber. Ia dibangun ulang dari event terurut (kuarter → countdown clock → realTime → youtubeTimestamp) oleh rebuildPossessionsEngine. Opening/closing/outcome diisi mesin. Anomali ditandai, tidak dihapus diam-diam. Koreksi manusia memperbaiki event, lalu rebuild.

DP-05 — Event Link Graph

Hubungan antar event disimpan eksplisit di EventLink: ASSISTS, STEALS_FROM, REBOUNDS, RESULTS_IN_FT. Jangan hanya mengandalkan urutan waktu. Helper wajib: createAssistShotLink, createStealTurnoverLink, createReboundShotLink, createBlockShotLink, createFoulFreeThrowLink.

DP-06 — Production Pipeline + Return

Empat tahap linear dengan dua jalur balik. Tidak ada lompat tahap. Setiap transisi menulis stageHistory (advanced | returned + user + waktu + note).

DP-07 — Trust Classification

Audit menghasilkan healthScore 0–100 dan kelas TRUSTED / CAUTION / UNRELIABLE. Temuan punya severity, grouping, dan suggestion (LINK_ASSIST, INSERT_REBOUND, LINK_STEAL, CLOSE_POSSESSION, REASSIGN_PLAYER, ADJUST_STINT_TIME). Resolusi disimpan di audit_issue_resolutions. Skor adalah sinyal kepercayaan publik, bukan kosmetik UI.

DP-08 — Visibility Triangle

Siapa boleh melihat match/story diputuskan hanya oleh canViewMatch:

  1. admin / statistician / coach → ya.
  2. customer → ya jika canManage (link guardian verified) ATAU ada PaymentRecord.status === 'success' yang requestId-nya = match.id ATAU childId ATAU athlete.id.
  3. scout → ya hanya jika productionStage === 'published' DAN minimal satu atlet isDiscoverable.

Dilarang menambah bypass “kalau login boleh lihat semua”. Story, PDF, dan clip YouTube memakai fungsi yang sama.

DP-09 — Canonical Team Key

Satu tim sah = (organizationId, divisionCode). teamRepo.findCanonical wajib dipanggil sebelum create. Nama tampilan boleh beda; kunci tidak. Divisi master: KU 8–19 × M/F/MIX → KU{n}-M|F|MIX.

DP-10 — Merge with Rollback Snapshot

Dua identitas yang sama (pemain atau org) disatukan ke primary. Secondary archived/merged + mergedIntoId. Semua FK (roster, event, stint, klaim, insight, transfer) dipindah. MergeLog menyimpan snapshot untuk undoMerge. Org merge men-cascade tim: jika target sudah punya canonical division yang sama, roster digabung.

Deteksi duplikat pemain: nama mirip (token/prefix) DAN DOB selisih ≤ 2 hari. Primary = yang lebih lengkap (avatar, displayName, jersey).

DP-11 — Claim-to-Guardian

Alur wajib lima langkah: search → teaser (PPG/RPG/APG, jumlah laga) → form (ayah/ibu/wali + dokumen) → payment → pending review. Approve menulis AthleteLink { relationship: 'guardian', verified: true } dan claimStatus: verified. Reject: refund_pending; claimStatus kembali unclaimed hanya jika tidak ada guardian verified lain (multi-guardian safety). Opsional merge placeholder lokal ke profil resmi.

DP-12 — Labor Marketplace (Request → Assign → Produce)

Customer tidak mencatat laga jasa. Mereka membayar request. Admin menugaskan statistician. Statistician membuat match dari request (idempotent jika matchId sudah ada), mencatat, lalu masuk DP-06. Back-office request: price 0, status langsung paid, customerId: 'back-office' — untuk laga internal tanpa checkout.

Status request: pending → awaiting_payment → paid → assigned → in_progress → completed → reviewed. Jangan loncat, jangan reuse status klaim.

DP-13 — Triple Clock Alignment

Tiga lapisan, urutan prioritas saat konflik: (1) titik MANUAL_CORRECTION, (2) OCR_CONFIRMED visual sync, (3) on-the-fly per event jika confidence ≥ 75, (4) automatic timeline published. Pipeline otomatis: DRAFT → SCANNING → REVIEW_REQUIRED → READY_TO_PUBLISH → PUBLISHED | FAILED. Fail-fast jika region jam tidak valid. OCR batch hanya lewat server berautentikasi (TARGET; as-is belum auth).

DP-14 — AI Reads Structure, Not Film

AI Coach (skill_coach, shot_analyst, progress_analyst, team_analyst, strategist, scout) membaca agregat event/possession, bukan frame video. Vision hanya untuk dua tugas: lineup jersey (hingga 16 frame) dan OCR jam. Output coach: { role, title, content, actionableAdvice[] } disimpan AiInsight. Bahasa: Indonesia + istilah Inggris baku.

DP-15 — RBAC as Data

Permission adalah string katalog, bukan if-role di komponen. Role → permission[] hidup di store role_permissions, diedit admin, bisa di-reset ke default. Komponen memakai can(permission) / RequirePermission. Admin lolos semua. TARGET: evaluasi yang sama di server.
